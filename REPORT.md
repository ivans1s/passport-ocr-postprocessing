# Отчёт: постобработка OCR паспорта РФ

## Что сделано

Решение — детерминированный постпроцессор без использования ML. Написан на чистом Python (только стандартная библиотека), работает на CPU без доступа к интернету. Для каждого документа скрипт выдаёт `accept` (с извлечением 10 полей) или `reject`.

Логика состоит из трёх уровней проверки:

1. **Действительность паспорта на 01.10.2026.** Дата выдачи берётся из MRZ (если он есть), иначе из визуальной зоны. Паспорт считается недействительным, если с даты выдачи прошло больше 20 лет. На train это отсекает 493 документа (16.4%) без риска зарезать валидные.
2. **Кросс-чек VZ ↔ MRZ.** Из MRZ (TD1-подобный формат, 2 строки по 44 символа) извлекаются: номер (серия + номер), дата рождения, пол, дата выдачи, код подразделения. Для номера и даты рождения проверяются **контрольные цифры** (алгоритм 7-3-1). Если контрольные цифры сошлись — MRZ считается надёжным. При расхождении с визуальной зоной документ отклоняется. При совпадении значения дат/пола/кода/номера берутся из MRZ.
3. **Фильтр по уверенности символов (`min(char_conf)`).** Для полей, которых нет в MRZ (ФИО, `Birth_place_ru`, `Issue_organization_ru`), проверяется минимальная уверенность OCR по буквам/цифрам. Если она ниже порога — документ отклоняется. Порог подобран на train (см. раздел «Выбор порога»).

Документы без MRZ (6.1%) проходят более строгую проверку: все поля непустые, средняя уверенность ≥ 0.99, уверенность символов ≥ 0.95, дата выдачи валидна.

## Анализ данных и ключевые наблюдения

**MRZ — главный источник истины.** У 94% документов MRZ есть. При совпадении контрольных цифр точность полей: `Birth_date` — 100%, `Sex_ru` — 100%, `Issue_date` — 99%, `Issue_organisation_code` — 97.5%. Поэтому кросс-чек VZ↔MRZ даёт почти идеальные даты/пол/код/номер: на train среди принятых — единицы ошибок в этих полях (1–3 на 1403).

**Главная проблема — `Birth_place_ru` и `Issue_organization_ru`.** Их нет в MRZ. Справочник `subdivisions.csv` **не совпадает** с разметкой по формулировкам (разные сокращения и порядок слов). Поэтому проверка названия по справочнику не работает: она либо пропускает ошибки, либо режет валидные. Средняя уверенность поля (`conf`) тоже **не разделяет** правильные и ошибочные значения (медианы 0.999 vs 0.986 — сильно пересекаются).

**Единственный работающий сигнал для этих полей — минимальная уверенность по символам (`min(char_conf)`).** У ошибочных значений медиана `min(char_conf)` ~0.6, у правильных ~0.99. Порог 0.95 убирает ~85% ошибок в этих двух полях.

**ФИО.** MRZ содержит ФИО латиницей (`ZAINTINOV`), обратная транслитерация неоднозначна (`I` = `И`/`Й`, `E` = `Е`/`Э`) и усугубляется OCR-ошибками в самой MRZ (`4UBUK` вместо `SHUBUK`). Поэтому MRZ для ФИО не используется. Визуальная зона даёт 95–97% точности; оставшиеся ошибки — «тихие» (уверенность 1.0, но буква не та) — фильтр символов ловит их лишь частично. Это осознанное ограничение решения.

## Выбор порога уверенности: сравнение вариантов

Ключевой параметр — порог `min(char_conf)`, ниже которого поле считается ненадёжным. Прогнаны 4 варианта на train; MRZ-кросс-чек одинаковый, различается только фильтр уверенности.

| Вариант | Фильтр `char_conf` | accept | precision | recall |
|---|---|---|---|---|
| C. Без фильтра | — | ~1780 | ~73% | ~60% |
| B1. Только 2 текстовых, 0.99 | `Birth_place`, `Issue_organization` | 704 | 90.5% | 21.2% |
| A. Все 5 полей, 0.99 | ФИО + 2 текстовых | 553 | 93.0% | 17.1% |
| **B3. Все 5 полей, 0.95 (выбран)** | ФИО + 2 текстовых | **1403** | **93.2%** | **43.6%** |

**Почему выбран B3:**
- Вариант C (precision 73%) противоречит ТЗ («не принять ни одного с ошибкой»).
- Варианты B1 и A (precision 90–93%) дают мало accept (17–21% recall) — избыточно осторожны.
- Вариант B3 даёт **ту же precision** (93.2%), что и A, но **recall в 2.5 раза выше** (43.6% vs 17.1%). Ужесточение порога с 0.95 до 0.99 не улучшает precision, но режет recall. B3 — оптимальный баланс для ТЗ.

## Результат на train

- **Документов:** 3000
- **Принято всего:** 1403 (46.8%)
- **Принято верно:** 1307 (43.6%)
- **Принято с ошибкой:** 96
- **Precision:** 93.16%
- **Recall:** 43.57%
- **Отклонено:** 1597 (53.2%), из них были валидны: 1119.

Ошибки среди принятых: ФИО — 37, `Birth_place_ru` — 27, `Issue_organization_ru` — 27, остальное (даты/код/номер) — 5.

## Результат на test и прогноз

- **Документов:** 2000
- **Принято:** 936 (46.8%)

Экстраполяция train-метрик: **~872 верных, ~64 ошибки, precision ~93%, recall ~43.6%**. Распределение причин reject-а на test пропорционально train — значит, test и train из одной генеральной совокупности, и train-метрики переносятся.

**Прогноз для сдачи:** из 2000 документов test ожидаю принять **936**, из них **~64 окажутся с ошибкой** (precision ~93%). Ошибки — почти исключительно в ФИО и двух свободных текстовых полях.

## Ограничения и что улучшить

1. **Транслитерация MRZ → кириллица** (ICAO Doc 9303) с перебором вариантов и сравнением с визуальной зоной позволила бы использовать MRZ как второй источник для ФИО и поднять precision до ~98% при том же recall. Не реализовано: обратный транслит неоднозначен, а MRZ содержит OCR-ошибки — это 1–2 дня дополнительной работы.
2. **Справочник с формулировками, совпадающими с разметкой**, убрал бы ошибки в `Issue_organization_ru` без потери валидных.
3. **Порог уверенности** — это компромисс precision/recall: 0.95 даёт precision 93% / recall 44%, 0.99 — precision 93% / recall 17% (без выигрыша в precision).
